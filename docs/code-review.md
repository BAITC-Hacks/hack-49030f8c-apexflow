## Блокеры интеграции аналитики

Статическая проверка `origin/codex/dev-maxim` на `809c072` выявила:

1. **Несовместимость контракта.** `analytics.assign_clusters` возвращает
   `cluster-001`, …, тогда как `00-contracts.md` требует целые `cluster_id`.
   Общий валидатор отклонит результаты. Исправление требуется согласовать
   с разработчиком 2 вместе с методологией и контрактными тестами.
2. **Потеря точности порядка gid.** `features._gid_key` преобразует числа
   во float. Разные int64 выше `2**53` могут получить одинаковый ключ;
   обещанная независимость построения графа/кластеров от порядка строк
   не гарантирована. Нужны целочисленная сортировка и регрессионный тест.
3. **Петля — не отсутствие операций.** `is_isolated` определяется по
   числу внешних контрагентов. Узел только с самопереводами при этом имеет
   наблюдаемые рёбра. `make_evidence` не должен писать об отсутствии
   входящих/исходящих связей, а правило transit не должно трактовать одну
   петлю как транзит между контрагентами.
4. **Объяснения и ограничения.** Для peripheral выводится общее описание
   без рассчитанных числовых наблюдений; ограничение входящих seed не
   добавляется в CSV evidence. UI показывает оговорку отдельно, но это
   не исправляет экспортируемое объяснение. Нужны тесты по каждой роли,
   seed и depth=4; ограничение длины должно сохранять важные оговорки.
5. **Крайние веса требуют проверки.** Общий контракт допускает конечные
   числовые суммы без явного правила для нулевых/отрицательных значений,
   а аналитика использует взвешенный Louvain и `log1p` оборота. До выпуска
   нужно согласовать политику входных сумм и проверить нулевые веса,
   отрицательные суммы, переполнение агрегатов и малые компоненты.

Эти выводы по удалённой ветке не являются результатом её контейнерных тестов.
Не подменять аналитику UI-эвристиками и не ослаблять общий контракт, чтобы
скрыть несовместимость.
