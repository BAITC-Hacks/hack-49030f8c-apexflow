# Приёмка интегрированного ApexFlow

Дата: 23 сентября 2026. Этот документ фиксирует выполненные проверки и внешние
ограничения; исходные планы в `docs/team/` сами по себе не означают приёмку.
Точные версии кода, входные хэши и длительность каждого свежего расчёта находятся
в локальном `output/run_manifest.json`. Реальные CSV и Parquet в Git не входят.

## Окружение

- Хост: Apple M2, 8 CPU, 16 GiB RAM, Docker Desktop 29.8.0.
- Docker VM: aarch64, 8 CPU, 8 319 770 624 байт RAM.
- Runtime: Python 3.12, pandas 2.2.3, NetworkX 3.4.2, PyArrow 18.1.0,
  Streamlit 1.41.1; точная версия Python записывается в manifest.
- Прямые зависимости закреплены в `requirements*.txt`; первоначальная сборка
  требует доступа к реестру образов и пакетам. Анализ после сборки выполняется
  с `network_mode: none`.

## Воспроизводимые проверки

```bash
export APEXFLOW_REVISION=$(git rev-parse HEAD)
docker compose --profile test run --rm --build tests
docker compose build pipeline ui
docker compose run --rm pipeline python -m scripts.verify_dataset
docker compose up --force-recreate --wait --wait-timeout 120 ui
docker compose exec -T ui python -m scripts.ci_smoke verify /app/data /app/output
docker compose exec -T ui python -m ui.demo_examples
```

`scripts.verify_dataset` повторяет полный расчёт, проверяет байты трёх CSV,
равенство после перестановки строк, все gid в загрузчике UI, изоляты, ограничения
seed/depth=4 и неизменность исходников. Он печатает агрегированный JSON-отчёт.
Это локальный прогон реальных данных, а не замена браузерной проверки.

## Статус общей проверки

Финальный совместный прогон зон 1 и 3 выполняется после объединения их изменений.
Результаты будут записаны здесь фактическими числами; промежуточные проверки
отдельных веток не объявляются успешным финальным релизом.

## CI и выпуск

`container-ci` выполняет четыре проверки: `release-source`, `static-demo`,
`compose-and-tests`, `runtime-smoke`. Последняя генерирует явно синтетические
Parquet внутри образа, запускает настоящий CLI и зависимый UI, проверяет хэши,
поиск всех клиентов и HTTP readiness. CI не загружает реальные банковские
Parquet; полный реальный прогон проводится отдельно в разрешённом окружении.

PR в `main` допускается только из `staging` этого репозитория. Этот CI-контроль
не заменяет техническую защиту веток. 23 сентября GitHub API показал
`protected: false` у `main` и `staging`; страница Settings текущего аккаунта
показала `You don't have access to repository options`. Настройки защиты не
изменены. Администратору нужно включить PR, одобрение другого участника,
актуальные обязательные проверки выше и запрет force push для обеих веток.

Дополнительный внешний блокер: [run 35850585881](https://github.com/BAITC-Hacks/hack-49030f8c-apexflow/actions/runs/35850585881)
завершился до старта шагов. В аннотациях GitHub: `The job was not started because
your account is locked due to a billing issue.` Устранение биллинга требует
владельца аккаунта/организации. Локальные Docker-проверки не выдаются за зелёный
Actions. Выпуск через `staging → main` должен дождаться настоящих обязательных
проверок; отключать их или подставлять успешные статусы нельзя.

## Действия с участием команды

- Другой участник должен самостоятельно повторить README: проверки агентом
  не являются подтверждением запуска другим человеком.
- Пятиминутная командная репетиция и личное участие на площадке требуют команды.
  Подготовленный сценарий — [demo.md](demo.md).
- Сдача на платформе проверяется отдельно по фактическому подтверждению.
  Коммит, PR, зелёный CI и локальные CSV не означают, что решение уже отправлено.
