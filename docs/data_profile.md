# Профиль исходных данных

Проверено 23.09.2026 в Docker Desktop / Linux amd64. Источник — предоставленный
участником архив `data (1).zip`; извлечены только три Parquet, без файлов macOS.
Исходники не изменены, в Git и образ не включены. Это агрегированный профиль,
не выгрузка клиентских идентификаторов или операций.

97 одинаковых строк **не удаляются**: без уникального transaction_id нельзя
считать их ошибочными дублями. Неизвестных endpoints нет; по каждой паре совпадают
количество операций и сумма. Числа узлов/рёбер/операций/seed и период совпали с ТЗ.

Типы после загрузки: nodes — gid/depth int64, is_seed bool; edges — src/dst/n_tx
int64, depth int8, sum_kzt float64; transactions — src/dst int64,
date datetime64[ns], sum_kzt float64. Временные метки не дополняются выдуманными
часами; временная последовательность в пределах дня из этого профиля не следует.

Сверка сумм использует `math.isclose(rel_tol=1e-12, abs_tol=1e-9)` в KZT — только
для численной погрешности float, без округления до тенге или изменения исходников.
Целые денежные столбцы преобразуются в float **до** агрегирования, чтобы не
допустить переполнение int64. Отрицательные суммы явно отклоняются: текущая
аналитика не моделирует возвраты. Для нового источника денежных данных необходимо
отдельно согласовать точность, единицы и правила возвратов.

## Воспроизведение

```bash
docker compose down
docker compose run --rm --build pipeline python -m apexflow --acceptance --json
docker compose run --rm --no-deps pipeline python -m apexflow --verify-output
docker compose up -d --force-recreate ui
```

`--acceptance` проверяет 2248/3119/4840/81, июль 2026 и время pipeline <300 секунд;
он не превращает отсутствие полного набора в успешный skip. По умолчанию CLI
поддерживает другие непустые корректные наборы, включая маленькие синтетические.

Первый полный контейнерный прогон с новой оркестрацией: **3,143 секунды**, 88
кластеров, 20 строк топа. Время включает чтение, валидацию, аналитику, запись и
проверку CSV, профиль и сбор runtime-метаданных; не включает сборку образа,
запуск процесса Python и запуск UI. Это одно измерение, не SLA. Выделено Docker:
8 CPU, 7 236 882 432 байт RAM. Python 3.12.14, pandas 2.2.3, NetworkX 3.4.2,
PyArrow 18.1.0; разрешённые транзитивные версии закреплены в requirements-lock.txt.

Каждый успешный запуск создаёт локальные `data_profile.json`, `run_manifest.json`
и `run_status.json` рядом с тремя CSV. Manifest содержит хэши входов/выходов,
commit (если передан при сборке), хэш исходного кода, версии, длительности и
агрегаты. `--verify-output` обнаруживает изменённые файлы и неуспешный последний
запуск. Эти служебные файлы не меняют схемы трёх обязательных CSV.

Повторение другим участником и проверки на других платформах не заменяются
локальными результатами. Команды и оставшиеся интеграционные ограничения —
в [передаче разработчика 1](pipeline-handoff.md).
