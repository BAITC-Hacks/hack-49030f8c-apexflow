# Профиль исходных данных и воспроизводимость

Проверено 23 сентября 2026 года на трёх выданных Parquet. В документе только агрегаты и хэши; исходные файлы в Git не добавлены. Количество строк и seed совпадает с ТЗ. `validate_inputs` сверяет каждую направленную пару `edges` с суммой и количеством строк `transactions`; набор принят без исправления или удаления строк.

## Деньги, даты и сверка

| Показатель | Значение |
|---|---:|

| Общая сумма edges | 365 890 012,01 KZT |
| Общая сумма transactions | 365 890 012,01 KZT |
| Минимальная / максимальная сумма ребра | 5 000 / 4 400 000 KZT |
| Минимальная / максимальная транзакция | 5 000 / 3 000 000 KZT |
| Сумма edges.n_tx | 4 840 |
| Полностью совпадающие строки transactions сверх первого вхождения | 97 |

Обе стороны содержат одинаковые 3 119 направленных пар; суммы и количества по каждой паре совпадают в пределах погрешности представления float. Совпадающие строки транзакций **не удаляются**: в наборе нет уникального transaction_id, поэтому совпадение полей не доказывает ошибочный дубль. Их удаление нарушило бы согласованность edges.

Агрегирование денег использует `math.fsum`, что предотвращает переполнение суммы int64. Допуск сверки — `max(1e-9 KZT, 4 × ulp(left), 4 × ulp(right))`; это округление float, а не доля оборота. Неконечный суммарный оборот отклоняется. Исходные суммы и даты не нормализуются молча.

## Подтверждение свежести расчёта

`output/run_manifest.json` дополняет три обязательных CSV и не меняет их схемы. В нём записаны SHA-256 трёх входов и трёх CSV, UTC-время, версия Python/основных зависимостей, `revision` образа и отчёт о расчёте. Для точной привязки задайте `APEXFLOW_REVISION` равным проверяемому commit при сборке; значение по умолчанию `unknown` честно обозначает отсутствие привязки.

Перед загрузкой входов pipeline записывает `status=running`, после успешной записи и проверки CSV — `complete`; при ошибке — `failed`. UI принимает только `complete` с совпадающими хэшами. Это позволяет обнаружить замену даже одной транзакции или CSV и не выдавать старые результаты за новый успешный расчёт. Хэши подтверждают целостность локального комплекта, но не являются цифровой подписью.

Каждый CSV записывается через временный файл с повторным чтением. Три `rename` не дают групповой атомарности: во время пересчёта UI следует останавливать, затем запускать Compose заново по README. Если процесс оборван, статус `running` также блокирует просмотр.

## Выполненные контейнерные проверки

На Docker Desktop / Linux aarch64, Python 3.12.14, pandas 2.2.3, pyarrow 18.1.0, NetworkX 3.4.2 выполнен полный runtime pipeline: **0,6951 с** от начала функции `run_pipeline` до записи CSV и формирования отчёта. Получено 2 248 ролей, 88 кластеров и 20 строк топа. Финальная запись manifest, старт процесса, сборка/скачивание образа в это время не входят. Это измерение рабочей версии `dev1-review-uncommitted`, а не утверждение о проверенном release-коммите; актуальную интеграционную приёмку фиксируют отдельно.

Входы монтировались read-only; их хэши после расчёта совпали. Образ использовался без bind-mount исходного кода. Дополнительно синтетический runtime smoke создал 24 узла, включая изолят и gid больше `2**53`, запустил pipeline → UI через Compose и подтвердил поиск всех gid и HTTP 200. Отдельный Compose-запуск с отсутствующими Parquet вернул exit 1 и не запустил UI.

CI `container-ci` содержит реальные jobs `release-source`, `static-demo`, `compose-and-tests`, `runtime-smoke`. Runtime smoke использует явно синтетические данные: банковские Parquet в GitHub Actions не передаются, поэтому зелёный CI не заменяет полную локальную проверку разрешённого набора. Полный сценарий текущего release-кандидата и независимый запуск другим участником фиксируются отдельно перед выпуском. Фактический статус внешнего CI и ограничение GitHub Billing отражены в [приёмке](acceptance.md).
