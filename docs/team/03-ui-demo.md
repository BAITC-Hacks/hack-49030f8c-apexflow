# Разработчик 3: интерфейс, README и демонстрация

Твоя задача — сделать результат аналитики понятным AML-аналитику и воспроизводимым для жюри. Максим (разработчик 2) считает роли и приоритеты; разработчик 1 читает данные, запускает анализ и пишет CSV. Ты превращаешь их работу в экран с поиском, графом, карточками и убедительной проверяемой демонстрацией.

Перед началом прочитать `AGENTS.md`, `TEAM_PLAN.md` и `docs/team/00-contracts.md`. Ветка своя от staging, например `dev/ui`; PR только в staging. Все перечисленные экраны и функции ниже — задания на реализацию, а не уже работающий продукт.

## 1. Что должно получиться

**Банковский акцент и задача для призового выступления:** организуй путь «очередь проверок → клиент → связи → объяснение → ограничения → следующий шаг → выгрузка». Карточка должна опираться на реальные CSV и согласованные с Максимом рекомендации. Подготовь сдержанный, читаемый интерфейс с едиными обозначениями, понятными суммами и явными состояниями ошибок. На защите покажи факты и работу аналитика, а не только обзор экрана. Общая стратегия: [банковский сценарий и жюри](04-bank-and-jury.md).

Локальное приложение открывает три CSV и исходные nodes/edges. Пользователь видит топ, выбирает любой gid, находит его на направленном графе и понимает назначенную роль по числам. Все 2 248 узлов из выданного набора доступны для поиска, включая изоляты и малые компоненты.

UI не обязан одновременно рисовать весь граф и все подписи. Он обязан дать доступ ко всей сети и показать связи выбранного узла честно, без создания впечатления, что отфильтрованное окружение — весь граф.

## 2. Твои файлы

| Файл | Содержание |
|---|---|
| app.py | Основной Streamlit-экран, загрузка файлов, управление выбранным gid и фильтрами |
| ui/graph.py | Только если визуализация заметно разрастается: преобразование узлов/рёбер и HTML графа |
| ui/fixtures/ | Явно синтетический пример для разработки, если он нужен до реальных CSV |
| tests/test_ui.py | При наличии выделенной логики: поиск, выбор подграфа, безопасное представление gid |
| README.md | Русскоязычная инструкция запуска и проверки по фактическому состоянию проекта |
| docs/architecture.md | Одна схема входы → метрики → роли/кластеры → CSV → UI |
| docs/demo.md | Порядок 5-минутной защиты, команды и проверенные примеры |

UI обязательно запускается в Docker-сервисе ui, который настраивает разработчик 1. Приложение читает /app/data и /app/output; не использует пути конкретного компьютера. Проверь доступ из браузера хоста и работу визуализации внутри контейнерного сценария. Dockerfile/Compose меняет разработчик 1 по согласованию с тобой.

Не добавлять сложное деление на страницы и компоненты, пока одного app.py достаточно. В requirements.txt зависимости вносит разработчик 1: передай ему список библиотек до использования.

## 3. Шаг 1 — начать без ожидания аналитики

1. Принять схемы трёх CSV из общего договора.
2. Подготовить маленький искусственный набор с несколькими ролями, двумя группами, направленными рёбрами, boundary и изолятом. Если показываешь полноценный топ-20 в примере, в нём должно быть хотя бы 20 разных узлов; иначе явно написать, что тестовый набор меньше.
3. Хранить его отдельно от output настоящего пайплайна. На экране тестового режима писать «Синтетический пример; не результаты анализа исходных данных».
4. Подготовить общую компоновку и загрузчик. Позже заменить источник на реальные три CSV, не менять поля.
5. К первому совместному запуску переключить приложение на реальные результаты. Не оставлять автоматический fallback на красивый искусственный граф при ошибке чтения.

## 4. Шаг 2 — загрузка и проверка файлов

Предлагаемый интерфейс в app.py: `load_view_data(data_dir, output_dir)`. Он читает nodes_roles, clusters, top_nodes, а также nodes и edges; дополнительно transactions нужны только если действительно отображаются временные признаки.

Проверить:

- Все обязательные файлы существуют, названия колонок соответствуют договору.
- gid не преобразованы через float; для поиска целочисленное значение или строка полного идентификатора.
- Все узлы из nodes присутствуют в nodes_roles, кластеры существуют, gid топа доступны.
- Пользователь не смешал CSV от одного набора с nodes/edges другого. Минимальная проверка gid не доказывает идентичность сумм; используйте единый согласованный набор и свежий пересчёт.
- Пустой/повреждённый файл даёт понятное сообщение, а не пустой белый экран или непонятный traceback.

Кэширование допустимо для отзывчивости. Но CSV после пересчёта должны обновляться: ключ кэша привязать к версии/времени изменения входных файлов либо сделать явную кнопку перечитывания. Кнопка обновления должна реально перечитывать файлы, а не просто перерисовывать старый результат.

Если данных нет, показать путь ожидаемого файла и подтверждённую разработчиком 1 команду запуска пайплайна. Не запускать дорогостоящий полный анализ на каждое движение фильтра.

## 5. Шаг 3 — основной экран

Рекомендуемая компоновка одного экрана:

```text
ApexFlow — анализ транзакционной сети
Источник/период, число узлов, рёбер, seed и кластеров

[Поиск по gid] [Роль] [Кластер] [Режим окраски] [Обновить данные]

[Топ приоритетов / таблица выбранного кластера]

[Направленный граф выбранного окружения] [Карточка узла]

[Входящие связи] [Исходящие связи] [Скачать 3 CSV]
Ограничения наблюдения и формулировки гипотез
```

Это пример компоновки, не требование делать отдельные вкладки. При ограниченном времени лучше один работающий экран со всеми обязательными действиями.

Общая статистика берётся из файлов, а не из зашитых чисел 2 248/3 119. Подпись «показано 35 из 2248 узлов» должна отличаться от общего размера сети. Период брать из подтверждённого профиля/данных; не обещать текущие онлайн-транзакции.

## 6. Шаг 4 — таблица топа

Минимальные колонки: rank, gid, role в понятном русском отображении, priority_score, why. Дополнительно полезен cluster_id, полученный join с nodes_roles.

| Код роли | Подпись в интерфейсе |
|---|---|
| consolidator | Признаки консолидации |
| transit | Признаки транзита |
| distributor | Признаки распределения |
| terminal | Предполагаемый конечный получатель |
| coordinator | Структурный кандидат на координацию |
| peripheral | Недостаточно выраженных признаков / периферия |

При выборе строки обновляется выбранный gid, карточка и граф. Если выбранная библиотека не даёт удобно обработать выбор строки, рядом допустим selector по gid; не тратить час на синхронизацию кликов, когда задача решается обычным полем поиска.

Ранг приходит из top_nodes и не пересчитывается молча при фильтрации. Отфильтрованный список можно показать как часть глобального топа; если нужен «топ текущего кластера», строить его по уже готовому priority_score и явно так назвать.

Не показывать role_score как «вероятность виновности». Лучше пояснение: «Сила поддержки гипотезы по выбранным правилам; шкала не калибрована как вероятность».

## 7. Шаг 5 — поиск любого gid

1. Использовать текстовый ввод, чтобы не терять точность больших int64 в браузере.
2. Удалить пробелы по краям, проверить формат целого идентификатора.
3. Найти узел в полном nodes_roles, а не в текущем топе или видимой компоненте.
4. При успехе выбрать его, показать карточку и окружение.
5. Если текущий фильтр скрывает узел, явно сбросить/расширить фильтр либо сообщить и предложить показать найденный узел. Поиск не должен утверждать «не найден», если gid существует за пределами фильтра.
6. Для отсутствующего gid показать «Такого gid нет в загруженной выборке».
7. Для изолята показать один узел и текст «Наблюдаемых связей нет», не ошибку визуализации.

Внутренние JS-идентификаторы графа можно передавать строками. Метки, табличные значения и CSV должны сохранять исходный gid без научной нотации и округления.

## 8. Шаг 6 — направленный граф

Базовый вариант: визуализация PyVis, встроенная в Streamlit, либо другой согласованный локальный компонент. Все необходимые JS/CSS должны быть доступны после установки без CDN; проверить отключением внешней сети, не полагаться только на браузерный кэш.

Правила отображения:

- Ребро направлено строго `src → dst`.
- Стрелка видна при обычном масштабе; толщина может отражать sum_kzt, но шкалу ограничить, чтобы крупное ребро не перекрыло граф.
- Окраска переключается между ролями и кластерами. Легенда объясняет цвета.
- Выбранный узел заметно выделен; seed можно обозначить формой/обводкой, boundary — дополнительной меткой.
- Название роли в tooltip соответствует таблице и карточке.
- Выделенные соседи показывают реальные связи, без искусственного восстановления пропущенных рёбер.
- При работе с HTML текст из файлов экранировать, чтобы evidence отображался как текст, а не как исполняемая разметка.

Первый режим — выбранный узел плюс непосредственные входящие и исходящие соседи. Второй возможный режим — весь выбранный кластер. Дополнительный второй hop — после готовности MVP. Если подграф слишком большой, ограничивать отображение по понятному правилу и показывать число скрытых узлов/связей; полная таблица соседей остаётся доступна.

Не менять направление ребра ради layout. Не уменьшать полный список узлов поиска до выбранной компоненты. Для повторяемого демо фиксированный layout/seed желателен, но математические выводы не зависят от координат картинки.

Клик по узлу с открытием карточки — полезное улучшение, однако обязательный сценарий можно полностью закрыть текстовым поиском и выбором из таблицы, если компонент не поддерживает обратную связь без дополнительной разработки.

## 9. Шаг 7 — карточка узла и таблицы связей

Карточка:

1. Полный gid.
2. Роль в русском отображении и исходный код при необходимости.
3. evidence без искажения и расширения фактов.
4. role_score, priority_score и пояснение их различия.
5. Кластер, depth, is_seed.
6. Наблюдаемое число входящих/исходящих контрагентов и суммы.
7. Оговорки: boundary, seed с неполными входящими, отсутствие связей.

Таблица входящих: src, sum_kzt, n_tx. Таблица исходящих: dst, sum_kzt, n_tx. Сортировать по сумме, но позволить увидеть все связи выбранного узла. Обозначать KZT и использовать единый формат чисел.

Сумму `in_sum − out_sum` можно подписать только как наблюдаемую разницу потоков, если её вообще показываете. Подписи «баланс счёта», «прибыль», «отмыто денег» не следуют из данных и недопустимы.

Если пользователь выбрал depth=4, показать понятную оговорку рядом с ролью: «Выборка обрывается на четвёртом колене; отсутствие исходящих не доказывает, что деньги остались на счёте». Это помогает правильно интерпретировать результат, а не является техническим сообщением о реализации.

## 10. Шаг 8 — кластеры и выгрузки

Для кластера показать размер, число seed, внутренний оборот, top_gids и hypothesis. Пользователь должен перейти от top_gids к поиску/карточке. JSON в top_gids разбирать как JSON, не через eval.

Кнопки скачивания возвращают три исходных CSV актуального расчёта. Не подменять полный nodes_roles только видимыми строками фильтра; если добавлен экспорт фильтра, назвать его отдельно и не выдавать за обязательный результат.

Перед релизом попросить разработчика 1 пройти README в чистом окружении, а Максима — проверить методологию и примеры.

## 12. Шаг 10 — схема и 5-минутная защита

В docs/architecture.md достаточно одной понятной диаграммы с контейнерами pipeline/ui, внешними папками data/output и браузером пользователя. Она должна показывать реальные модули, входные файлы и три выхода. Не рисовать облачную инфраструктуру, которой нет.

В docs/demo.md зафиксировать примерно такой сценарий:

| Время | Кто говорит / делает | Что показываете |
|---|---|---|
| 00:00–00:30 | Ты | Вопрос аналитика и цель инструмента |
| 00:30–01:10 | Разработчик 1 | Живой запуск команды, реальные результаты и время |
| 01:10–02:00 | Ты | Топ, поиск gid, стрелки, фильтр роли/кластера |
| 02:00–03:30 | Максим | Два реальных узла с разными профилями и числовыми объяснениями |
| 03:30–04:10 | Максим + ты | Boundary/изолят и корректная работа с неполнотой |
| 04:10–04:40 | Ты | Кластеры, скачивание CSV, повторяемость по README |
| 04:40–05:00 | Вся команда | Ценность и честные ограничения |

Это план по времени; если живой расчёт занимает дольше, перестроить выступление вокруг него и отрепетировать, сохранив обязательный живой запуск. Ранее сохранённые результаты можно держать резервом, но при сбое прямо сказать о нём, не выдавать старые CSV за успешный текущий расчёт.

Выбрать реальные демонстрационные gid после расчёта вместе с Максимом. Сохранить их в сценарии демо допустимо; зашивать их в алгоритм вместо вычисления запрещено. Жюри также может назвать любой другой gid.

## 13. Проверки интерфейса

- [ ] Приложение запускается через Docker Compose из README без Python на хосте.
- [ ] UI стартует после успешного pipeline, читает смонтированные результаты и открывается на localhost:8501.
- [ ] Реальные данные отделены от синтетического режима.
- [ ] Глобальный топ показывает ≥20 узлов на полном наборе.
- [ ] Обычный gid находится и открывает правильную карточку.
- [ ] Находится gid из малой компоненты, изолят и узел depth=4.
- [ ] Отсутствующий/некорректный gid даёт понятное сообщение.
- [ ] Активный фильтр не скрывает найденный gid без объяснения.
- [ ] На проверенной паре A→B стрелка указывает от A к B, суммы совпадают с edges.
- [ ] Роль, score и evidence совпадают с CSV.
- [ ] Отсутствующие файлы не заменяются тихо искусственным набором.
- [ ] После пересчёта результаты обновляются; скачивание возвращает полные CSV.
- [ ] Граф отображается без внешней сети после установки зависимостей.
- [ ] Второй участник воспроизводит сценарий по README.

Для тестов выбирать содержательную логику: поиск при активном фильтре, изолят в подграфе, точное преобразование большого gid. Не писать тесты, которые лишь повторяют строки отрисовки Streamlit. Реальную визуальную проверку стрелок и читаемости выполнить в браузере.
