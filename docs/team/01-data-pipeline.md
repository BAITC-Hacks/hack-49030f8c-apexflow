## 3.1. Обязательная настройка Docker — твоя ответственность

Docker входит в MVP по прямому требованию команды. Он должен охватывать всё исполняемое окружение приложения: загрузку и анализ данных, экспорт, интерфейс, тесты. На хосте допустимы Docker/Compose, Git, редактор, браузер, входные файлы, результаты и инструменты агента. Контейнеризация одного UI при обязательном ручном запуске Python-пайплайна на хосте не считается выполнением.

### A. Образ

1. Создать один Dockerfile с общей Python runtime-базой. pipeline и ui различаются командами, а не отдельными несовместимыми окружениями.
2. Выбрать конкретную совместимую версию базового образа, не `latest`; перед финальной сдачей зафиксировать проверенную версию, при необходимости digest. Не придумывать digest без проверки.
3. Сначала копировать файлы зависимостей и устанавливать пакеты, затем копировать код: изменение аналитики не должно каждый раз требовать скачивания всех библиотек.
4. Задать рабочую папку `/app` и PYTHONPATH=/app/src либо проверенную установку пакета внутри образа. Абсолютные пути с компьютера конкретного разработчика не использовать.
5. Добавить test-target на основе той же runtime-базы с тестовыми зависимостями. tests использует отдельный target/tag, не перезаписывающий runtime-образ.
6. Выполнять установку зависимостей во время сборки; pipeline/UI не должны делать pip install или скачивать библиотеки при каждом старте.
7. Предусмотреть обычного пользователя контейнера и права записи в смонтированный output. Проверить Linux UID/GID и используемые в команде Docker Desktop; не решать проблему глобальным chmod 777.
8. `.dockerignore` исключает `.git`, `.venv`, кэши, `.env`, ключи, настоящие `data/` и `output/`, PDF задания. Явно синтетические тестовые fixtures, если используются, оставить доступными test-target.

### B. Docker Compose

| Сервис | Команда/назначение | Доступ к файлам | Жизненный цикл |
|---|---|---|---|
| pipeline | `python -m apexflow --data /app/data --output /app/output` | data: read-only; output: read-write | Одноразовый job; код 0 только при успешном расчёте; без бесконечного restart |
| ui | Streamlit на 0.0.0.0:8501 внутри контейнера | data и output: read-only | Стартует после успешного pipeline; доступ с хоста localhost:8501 |
| tests | Запускает согласованный набор тестов | Синтетические fixtures/входы: read-only; результаты во временной папке | Отдельный профиль `test`; не запускается при обычном старте UI |

Для ui настроить `depends_on` с `condition: service_completed_successfully` на pipeline. Сам факт, что процесс pipeline стартовал, не означает готовности CSV. Если pipeline завершился с ошибкой, свежий ui не должен стартовать на старых результатах. Такая зависимость описана в [документации Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/).

Опубликовать UI только локально, например 127.0.0.1:8501:8501. Добавить healthcheck реальной HTTP-готовности UI без установки утилиты только ради проверки, если достаточно стандартной библиотеки Python. Готовность страницы не заменяет проверку поиска и визуализации.

### C. Постоянство данных и повторный расчёт

- `./data` монтируется в `/app/data` только для чтения. Пайплайн не должен менять исходники.
- `./output` монтируется в `/app/output`; три CSV остаются доступны на хосте после удаления контейнеров.
- UI читает output, но не перезаписывает результаты. tests не использует demo-output как временный каталог.
- Проверить старт с пустой output и создание папки с корректными правами. Не запекать готовые CSV в образ ради успешного демо.
- При повторном расчёте сначала остановить UI, затем создать новый запуск pipeline. Обычный restart UI не должен считаться пересчётом.
- Ненужные секреты/файлы пользователя не монтировать. Если позже появится optional LLM, ключ передавать только сервису, которому он нужен, через окружение/секреты; в образ и Git ключ не помещать.

### D. Целевые команды для README и коллег

Команды ниже начнут работать после твоей реализации Compose; сейчас это контракт:

```bash
# Сборка, новый расчёт и запуск интерфейса
docker compose up --build --force-recreate

# Контейнерные тесты
docker compose --profile test run --rm --build tests

# Журналы
docker compose logs pipeline ui

# Остановка; входы и CSV на хосте сохраняются
docker compose down
```

Для повторного полного запуска выполнить down, затем основной up. Параметр force-recreate предназначен для пересоздания даже неизменившихся контейнеров; build выполняет сборку перед стартом — [справочник команды up](https://docs.docker.com/reference/cli/docker/compose/up/). Профиль test отделяет тестовый сервис от обычного запуска — [профили Compose](https://docs.docker.com/compose/how-tos/profiles/).

Первый сквозной запуск должен работать без bind-mount исходного кода: приложение берётся из собранного образа. Дополнительный dev-режим с монтированием кода допустим, если ускоряет работу команды, но не заменяет проверку релизного образа.

### E. Что проверить до признания Docker готовым

- [ ] На хосте не нужен Python/pip/venv для основного запуска и тестов.
- [ ] Свежая сборка устанавливает все зависимости и включает нужный код.
- [ ] pipeline завершается успешно, три CSV появляются на хосте.
- [ ] ui ждёт успешного расчёта и открывается через браузер.
- [ ] Ошибка входных данных даёт ненулевой exit code и не запускает свежий ui.
- [ ] Повторный запуск действительно пересчитывает данные.
- [ ] После down результаты сохраняются, исходные файлы не изменяются.
- [ ] Тесты проходят в контейнере, не перезаписывая результаты демо.
- [ ] Основной сценарий после сборки не требует сети/CDN/API.
- [ ] Проверены используемые командой платформы; ограничения CPU/RAM и архитектуры записаны.

Не нужны Kubernetes, отдельная БД и дополнительные сервисы без задачи. Общего образа и Compose достаточно для заявленного MVP.

## 4. Шаг 2 — прочитать и проверить данные

Предлагаемый интерфейс в `io.py`:

```python
def load_inputs(data_dir):
    # return nodes, edges, transactions
    ...

def validate_inputs(nodes, edges, transactions):
    # raise ValueError с причиной при нарушении
    ...
```

Последовательность:

1. Проверить наличие ровно необходимых входных файлов по известным именам. Лишние файлы в data не должны ломать чтение.
2. Прочитать Parquet через согласованный движок и вывести реальные типы.
3. Проверить обязательные колонки; дополнительные допустимо сохранить, но не превращать в выдуманные признаки клиента.
4. Проверить gid, src/dst, depth, is_seed, суммы, n_tx, даты по общему договору.
5. Проверить уникальность nodes.gid, полноту ссылок рёбер и транзакций.
6. Выяснить повторные пары edges. Простое создание DiGraph из дублирующихся пар перезапишет данные; разрешить неоднозначность до передачи Максиму.
7. Агрегировать transactions по `(src, dst)` и сопоставить сумму и количество с edges. Проверить отсутствующие пары в обе стороны. Допуск на суммы определить по реальной точности источника и задокументировать.
8. Проверить период, минимальные/максимальные суммы и распределение depth. Расхождения с PDF отдельно записать и выяснить; не менять файлы, чтобы «совпали цифры».

Ошибка схемы останавливает запуск. Замечание вроде присутствия self-loop сначала отражается в профиле и передаётся Максиму; его нельзя молча удалить. Не удалять одинаковые строки транзакций без уникального ID операции.

В `docs/data_profile.md` записать только агрегаты: хэши и размеры файлов, число строк/уникальных gid/seed, распределение depth, даты, суммы, пропуски, повторы, результаты сверки edges ↔ transactions. Не публиковать полный набор автоматически при подготовке профиля.

## 5. Шаг 3 — сделать команду запуска

В `__main__.py` использовать стандартный `argparse`; обязательные пользовательские параметры — `--data` и `--output`, значения по умолчанию data и output. В `pipeline.py` одна функция `run_pipeline(data_dir, output_dir)` связывает этапы.

Порядок выполнения:

1. Запомнить время начала через монотонный таймер.
2. Загрузить и проверить три исходные таблицы.
3. Вызвать `analyze(nodes, edges, transactions)` из аналитики Максима.
4. Проверить наличие всех трёх ключей словаря и инварианты таблиц.
5. Сохранить CSV сначала во временную папку/файлы и проверить возможность их повторного чтения.
6. Опубликовать итоговые файлы только после успешной проверки всех трёх. Не заявлять групповую атомарность, если используется три отдельных rename; для MVP не запускать UI одновременно с перезаписью результатов.
7. Вывести число узлов, кластеров, строк топа, время и место сохранения.
8. Вернуть успешный код только при успешном завершении всех этапов.

При сбое показать этап и причину: например «В edges есть src, отсутствующий в nodes» или «В nodes_roles пропущены 19 gid». Не перехватывать все исключения с безусловным `return 0`. Если остались старые результаты, не называть их результатом текущего запуска.

До готовности Максима I/O можно проверять на тестовой функции, возвращающей искусственные DataFrame; она должна существовать только в тесте. Не оставлять скрытый fallback на фальшивые роли в рабочем CLI.

## 6. Шаг 4 — проверить три результата

Предлагаемый интерфейс `validate_outputs(results, nodes, edges)` в `io.py`.

Проверки nodes_roles:

- Множество gid в точности равно nodes.gid; нет дублей и потерянных изолятов.
- Роль из словаря; оба score конечные и от 0 до 1.
- У каждого есть cluster_id; он присутствует в clusters.
- evidence не пуст после удаления пробелов, длина не больше 200 символов.

Проверки clusters:

- Уникальные cluster_id, нет «пустых» кластеров без узлов.
- n_nodes и n_seed точно совпадают с группировкой nodes_roles и nodes.
- Сумма n_nodes равна числу входных узлов; сумма n_seed равна общему числу seed.
- Внутренний оборот пересчитывается по исходным направленным рёбрам без двойного счёта встречных переводов.
- top_gids — валидный JSON-массив, все элементы принадлежат этому кластеру; hypothesis заполнена.

Проверки top_nodes:

- Не меньше 20 уникальных узлов на основном наборе.
- rank непрерывный от 1; порядок соответствует score и правилу разрешения равенств.
- role и priority_score совпадают с nodes_roles для того же gid.
- why заполнено, содержит объяснение, а не техническую ошибку или заглушку.

После записи повторно прочитать три CSV и проверить сохранение схем/идентификаторов. Тест с gid больше `2**53` поможет поймать преобразование через float; это защита формата, а не утверждение, что такие gid есть в текущем наборе.

## 7. Шаг 5 — проверки и CI

Минимальные содержательные тесты:

| Сценарий | Ожидаемое поведение |
|---|---|
| Корректный небольшой набор | Созданы три читаемых CSV; сохранены все узлы |
| Нет nodes.parquet / нет обязательной колонки | Понятная ошибка, ненулевой код |
| Дублирован gid или неизвестный endpoint | Запуск остановлен до аналитики |
| Аналитика вернула NaN / потеряла узел / неверный cluster_id | Результат отклонён |
| evidence с запятой и переводом строки | CSV после повторного чтения хранит тот же текст |
| Изолированный узел | Присутствует в итоговой таблице и своём кластере |
| Полный согласованный датасет | Все must-have, время <5 минут |

CI внедрять после появления работающих команд, не создавать зелёный workflow с одними echo. Предлагаемые этапы:

1. Checkout и проверка конфигурации Compose (`docker compose config --quiet`).
2. Сборка runtime-образа и test-target в Docker; Python-зависимости устанавливаются внутри образов.
3. Контейнерные тесты входов/контрактов и аналитики на синтетических данных.
4. Запуск pipeline в контейнере с разрешённым набором; проверка CSV и времени; сохранить exit code одноразового job как обязательный результат CI.
5. Запуск UI из того же собранного runtime-образа, проверка HTTP-готовности; ручное демо дополнительно проверяет поиск и визуальные стрелки.
6. При завершении/ошибке сохранить логи и результаты проверок, остановить контейнеры. Успешный запуск только на Python хоста не заменяет этот CI.

Если полный датасет нельзя хранить в репозитории, определить разрешённый защищённый способ доставки для CI. На обычных PR допустим отдельный набор синтетических проверок; release-проверка полного сценария не считается выполненной, если нужные данные отсутствуют. Не использовать `continue-on-error` для обязательной проверки и не превращать отсутствие набора в зелёный skip.

Настроить запуск для PR в staging/main и новых коммитов staging. В защиту веток включить реальные стабильные имена обязательных jobs после их появления. Если прав администратора или тарифа GitHub недостаточно для защиты, сообщить ограничение; документ не делает запрет технически действующим.

## 8. Шаг 6 — интеграция и выпуск

До merge PR проверить: правильная base staging; изменены согласованные файлы; нет ключей; команды работают; обязательные проверки текущего PR прошли. После merge новой аналитики сразу запустить пайплайн и UI вместе.

Выпуск:

1. Зафиксировать, какой коммит staging кандидат в релиз.
