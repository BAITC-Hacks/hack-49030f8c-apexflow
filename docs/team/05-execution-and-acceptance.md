# Подробная рабочая карта ApexFlow: задачи, зависимости, приёмка и сдача

Этот документ переводит согласованный план в конкретные задания для трёх людей. Он не утверждает, что перечисленные функции уже реализованы. Рабочий код создаётся в период хакатона в соответствии с правилами организаторов; сейчас подготовлены инструкции.

Максим — разработчик 2, ветка `codex/dev-maxim`. Разработчик 1 отвечает за данные, Docker и интеграцию; разработчик 3 — за интерфейс и сдаваемую документацию. Общий контракт: [00-contracts.md](00-contracts.md). Формулы и реализация описаны в отдельных инструкциях участников.

## 1. Какие решения уже приняты

| Вопрос | Решение |
|---|---|
| Для кого продукт | AML-аналитик банка, исследующий транзакционную сеть |
| Основная задача | Найти важные узлы и объяснить порядок их проверки |
| Вход | nodes.parquet, edges.parquet, transactions.parquet |
| Обязательный выход | nodes_roles.csv, clusters.csv, top_nodes.csv + экран просмотра |

| Запуск | Docker Compose; Python на хосте не обязателен |
| Ветки | Личные ветки от staging → PR в staging → проверенный release PR в main |
| Production | Это назначение main; отдельной ветки prod нет |
| Кто принимает решение по клиенту | Специалист; система даёт гипотезы и приоритеты |
| Цель хакатона | Конкурентоспособное решение по критериям жюри и призовое место |
| Время | 5 часов; отведённый период разработки уточняется по объявлению организаторов |

## 2. Чего должен достичь банковский пользователь

### Сценарий S1: получить очередь проверок

Вход: согласованная выгрузка. Пользователь запускает Compose и получает результаты расчёта. Он открывает интерфейс, видит общую статистику и минимум 20 приоритетных узлов с причинами.

Приёмка: числа на экране получены из файлов; топ согласован с nodes_roles; новый запуск действительно обработал текущие данные; нет зависимости от скрытых ручных действий.

### Сценарий S2: проверить конкретного клиента

Пользователь вводит существующий gid, который может отсутствовать в топе. Система показывает карточку, направленные связи и кластер. Если узел не связан с другими, он всё равно находится.

Приёмка: поиск работает по полному набору; фильтр не маскирует найденный узел; полный gid не округлён; стрелки соответствуют src → dst.

### Сценарий S3: разобраться в гипотезе

Пользователь видит факты, выбранную роль, score и ограничения. Он может сопоставить объяснение со списком входящих/исходящих контрагентов.

Приёмка: числа проверяются по исходным рёбрам; роль и score взяты из результата аналитики; нет придуманных ФИО, профессии, доходов и других атрибутов.

### Сценарий S4: понять следующий шаг

Для depth=4 система объясняет ограничение глубины и предлагает уточнить последующие исходящие. Для seed — неполноту входящих. Для транзита — необходимость проверки дат, если временная поддержка ещё не рассчитана.

Приёмка: рекомендация относится к наблюдаемому ограничению; она не изображает автоматически отправленный запрос или доказанную виновность. Таблицу рекомендаций утверждает Максим, отображает разработчик 3.

### Сценарий S5: передать результат коллеге

Пользователь скачивает три полных CSV. Коллега получает код и те же входные файлы и воспроизводит расчёт.

Приёмка: CSV читаются, сохраняют gid и объяснения; в README есть команды и версии; повторный запуск даёт согласованный результат.

## 3. Три уровня приоритета

| Приоритет | Содержание | Можно убрать при нехватке времени? |
|---|---|---|
| P0: обязательный | Все пять must-have, три CSV, корректный граф, Docker, объяснения, README, схема, демо, сдача | Нет |
| P1: качество банковского сценария | Следующие шаги аналитика, ясные состояния UI, подтверждённые измерения, проверка случайного gid | Упрощать оформление, сохранять смысл и честность |
| P2: дополнительное преимущество | Временные признаки, анализ чувствительности, вычисляемый путь от seed | Да; только после работающего P0 |

Чат, обучение без разметки, новая БД, микросервисы, GPU и масштабирование на миллион узлов не добавляются ради количества функций. Масштабирование описывается текстом, как требует ТЗ.

Каждую задачу можно объединять с соседней в небольшой законченный PR. Не делать отдельный PR на каждую функцию, если это мешает интеграции. Не сливать в staging заведомо неработающий stub аналитики только для видимости прогресса.

Если A1 задержался, Максим и разработчик 3 могут продолжать в своих локальных окружениях для разработки, но приёмка их работы всё равно проходит в Docker. Это временная организация работы, а не отказ от требования контейнеризации.

## 8. Что передавать на каждой контрольной точке

### 01:00 — первые самостоятельные части

- A: профиль входов/загрузчик и состояние Docker-сборки.
- M: полный граф и проверенные простые признаки на искусственном примере.
- U: макет с поиском, таблицей и карточкой на обозначенном примере.

### 01:30 — совместимость

- M предоставляет первую реальную analyze с неизменёнными полями.
- A запускает её и сообщает конкретное нарушение контракта, если оно есть.
- U подтверждает, что схема реальных результатов подходит UI.

### 02:30 — первый сквозной сценарий

Исходные данные → pipeline → три CSV → браузер. Разрешены недоработки оформления и грубые, но объяснимые правила. Нельзя считать этот рубеж пройденным на искусственных результатах вместо выданных данных.

### 03:30 — готовность обязательного результата

Все пять must-have, Docker, README-команды, схема, проверка произвольного gid. Только после этого возможен один P2-пункт при наличии времени.

### 04:00 — весь состав на площадке, начинаем финальную стабилизацию

Согласно правилам участия последний час все находятся в зоне хакатона. Проверяем, что никто не остаётся с ключевым незакоммиченным модулем на отдельной машине. Новые крупные функции уже не начинаем; к 04:15 замораживаем любые новые функции.

### 04:30 — кандидат для выпуска

Зафиксирован commit staging, выполнен свежий контейнерный прогон, известны реальные демонстрационные gid и время. Если меняется код или данные — повторить затронутую проверку.

### До дедлайна — отправка

Проверенный release PR, итоговая main, доступные артефакты и подтверждённая сдача на платформе. Оставить запас на загрузку и технические ошибки, не планировать первую отправку на последнюю минуту.

## 9. Единый протокол интеграции

### Автор задачи

1. Сохраняет изменения в своей ветке с настоящим авторством.
2. Получает актуальную staging и разрешает конфликты в своей ветке.
3. Выполняет подходящие тесты и сообщает результат, включая неготовые проверки.
4. Открывает PR в staging с описанием задачи, командой воспроизведения и изменённым контрактом, если он согласован.

### Проверяющий

Проверяет факт работы и принадлежность файлов. Разработчик 1 смотрит аналитику на совместимость, Максим — входы/выходы и смысл проверки, разработчик 3 — понятность пользовательского результата. Автор не подменяет независимую проверку утверждением «у меня работает».

### Перед выпуском

Разработчик 1 проверяет актуальное интегрированное состояние, не только отдельные зелёные PR. Если main уже изменилась, проверяется результат будущего слияния. Публиковать итог в main напрямую из личной ветки нельзя.

Шаблон сообщения коллегам:

```text
Задача: M5 — analyze и три таблицы
Ветка/PR: <фактическая ссылка>
Готово: <конкретное поведение>
Проверка: <команда и фактический результат>
Контракт: <без изменений либо согласованные изменения>
Нужно от коллег: <что, от кого и к какой точке>
Осталось: <реальные ограничения>
```

Это пример шаблона, а не сообщение о выполненной M5.

## 10. Финальная приёмка: как жюри может проверить решение

Все пункты ниже имеют исходный статус «не проверено» до выполнения. Таблицы планирования не являются протоколом успешных тестов.

| Проверка | Действие | Ожидаемый результат | Владелец |
|---|---|---|---|
| T1 | Запуск Compose на машине без Python | Сборка, пересчёт, затем доступный UI | A |
| T2 | Проверка множества gid | Ровно исходное множество, без потерь/дублей | A + M |
| T3 | Сверка CSV | Колонки, типы, оценки, cluster_id и топ согласованы | A |
| T4 | Поиск обычного, граничного и изолированного gid | Все находятся, объяснения не противоречат данным | U + M |
| T5 | Выбор реального ребра | Направление и сумма в UI совпадают с edges | U |
| T6 | Выбор трёх случайных узлов | Команда объясняет правила и признаки | M |
| T7 | Проверка кластеров | Все узлы назначены, n_nodes/n_seed/оборот корректны | A + M |
| T8 | Полный повторный расчёт | Результат воспроизводим, время меньше 5 минут | A + M |
| T9 | Некорректный вход | Ненулевой код; свежий UI не выдаёт старые файлы за новый результат | A |
| T10 | Выключение внешней сети после сборки | Основной анализ и визуализация доступны | A + U |
| T11 | Остановка контейнеров | Исходники и CSV остаются на хосте | A |
| T12 | Проход по README другим человеком | Основной сценарий воспроизводится без устных подсказок | U + A |
| T13 | Репетиция пяти минут | Живой расчёт, 2–3 примера и ценность понятны в отведённое время | Все |
| T14 | Открытие платформы после отправки | Видно подтверждение актуальной сдачи | U |

Для T8 отдельно указать CPU/RAM, Docker-ресурсы и холодный/повторный запуск. Сборка образа — отдельное измерение. Для T9 запускать в тестовой копии набора, исходники data не портить.

## 11. Как собрать доказательства для жюри

| Утверждение на защите | Достаточное подтверждение для прототипа |
|---|---|
| «Обработали все узлы» | Проверка точного равенства множеств gid |
| «Пересчёт укладывается в лимит» | Измерение полного pipeline в Docker на указанной машине |
| «Решение воспроизводимо» | Повторный запуск и инструкция, проверенная коллегой |
| «Результаты объяснимы» | Конкретное правило + числа + реальные связи для выбранного gid |
| «Учитываем обрыв графа» | Тест boundary и реальный пример с правильной оговоркой |
| «Полезно аналитику» | Демонстрация очереди, разбора узла и обоснованного следующего шага |
| «Есть вклад AI-агента» | Конкретное описание помощи в разработке и выполненной человеком проверки |

Не заменять подтверждения процентами без измерений. Нет ground truth — нет заявлений об accuracy на реальном наборе. Детерминированность и полнота не равны правильности всех гипотез.

## 12. Демонстрационные примеры и ответы на вопросы

### Пример 1: важный non-seed

Выбрать после расчёта узел с выразительными подтверждаемыми признаками. Назвать gid, роль, фактическое число контрагентов, суммы и причину попадания в топ. Открыть связи и показать соответствие числам. Если такого убедительного примера пока нет, исследовать правила; не создавать историю про вымышленного организатора.

### Пример 2: другая структура потоков

Показать distributor или transit, если кандидат обоснован. Сравнить, какие признаки отличаются от первого примера и какое правило выбрало роль. Сходство входящих/исходящих само по себе не доказывает перевод одной и той же денежной суммы.

### Пример 3: ограниченная наблюдаемость

Открыть boundary либо изолированный seed. Показать, что система сохраняет клиента в данных, но не делает категорического вывода без оснований. Предложить следующий шаг по проверке отсутствующей информации.

| Вопрос жюри | Суть ответа |
|---|---|
| Почему не обучили модель? | Нет размеченных ролей; выбран проверяемый графовый baseline. Обучение возможно после появления допустимой разметки и процедуры валидации |
| Почему такие пороги? | Показать фактические распределения, выбранную эвристику и её ограничения; при наличии — проверку чувствительности |
| Почему этот узел в топе? | Назвать конкретные вклады метрик и исходные связи |
| Это вероятность преступления? | Нет; role_score — поддержка эвристической роли, priority_score — порядок проверки |
| Как работает без интернета? | Runtime-зависимости находятся в собранном образе; данные/CSV смонтированы; визуальные ресурсы доступны локально |
| Что будет на миллионе узлов? | Объяснить, какие расчёты и способы хранения/визуализации меняются; не утверждать, что этот масштаб уже испытан |
| Можно внедрить завтра? | Это проверенный на выданном наборе прототип; контур конкретного банка и требования к промышленной эксплуатации отдельно согласуются |

Формулировки адаптировать к реально выполненной работе. Если не измеряли чувствительность или не проверяли офлайн-режим, прямо назвать это, не использовать таблицу как основание для выдуманного результата.

## 13. Если что-то идёт не по плану

| Проблема | Действие | Что нельзя объявлять успешным |
|---|---|---|
| Не собирается Docker | A устраняет минимальную причину; остальные продолжают модули; запросить техническую помощь ментора по правилам | Основной сценарий только на хосте |
| Нет analyze к 01:30 | M отдаёт простой реальный baseline с полным контрактом, усложнение откладывает | Всем одинаковая роль ради количества строк без правил |
| Аналитика слишком медленная | Ограничить дорогую центральность, сохранить параметры и честно описать приближение | Таймер только удобной части вместо полного pipeline |
| Граф нечитаем | Показывать окрестность/кластер и таблицу связей, сохранить поиск всей сети | Скрыть неудобные компоненты из результата |
| Нет ground truth | Проверять инварианты, синтетические случаи, объяснимость | Придуманную точность модели |
| Нет доступа к защите веток | Зафиксировать ограничение, сохранить PR-процесс и реальные проверки | Якобы включённую техническую защиту |
| Нет данных в CI | Использовать разрешённый способ доставки; явно отделить synthetic-тесты от полного release-прогона | Зелёный skip полного прогона |
| Мало времени после 03:30 | Отменить P2, исправить P0, отрепетировать | Новую непроверенную фичу вместо обязательного результата |

## 15. Правила участия и личный вклад

Источник: PDF «Правила зачета участия.pdf» в корне проекта, страницы 1–2. Дубликат «Инструкция_для_участников_HackAlem_AI (1).pdf» побайтово совпадает с ранее прочитанной инструкцией и новых требований не добавляет.

- Каждый участник должен внести личный вклад; проект создаётся в рамках хакатона. Не представлять заранее готовый проект как созданный во время события.
- Каждый выполняет свою часть, запускает проверки и может объяснить решения. Собственные ветки, коммиты, PR и ревью помогают показать реальный вклад; не создавать искусственную историю авторства.
- До старта нужно находиться на площадке с корректно отсканированным личным бейджем; чужой бейдж использовать нельзя.
- После старта нельзя пересаживаться или переходить в другой сектор.
- Личные выходы суммарно ограничены 60 минутами, о выходе/возвращении сообщают стюарду и сканируют бейдж.
- Весь последний час нужно находиться в зоне хакатона; экстренный выход до 5 минут допускается с разрешения стюарда.
- Нельзя уходить до официального завершения. Технические вопросы адресуются ментору установленным способом.

Это требования организаторов из предоставленного документа. Если в день мероприятия организаторы официально уточнят порядок, команда сверяется с ними. Распределение задач не заменяет соблюдение правил зачёта участия.
