# Разработчик 2 — Максим: графовая аналитика

Твоя ветка — `codex/dev-maxim`, база — staging, целевая ветка PR — staging. Ты отвечаешь за содержательную часть решения: какие узлы важны, какая у них предполагаемая роль, как они связаны и почему аналитик должен смотреть их первыми.

Прочитай общий договор `docs/team/00-contracts.md`. Разработчик 1 загружает/валидирует данные и сохраняет результат; разработчик 3 показывает его. Тебе не требуется писать CLI, Dockerfile/Compose, CI и Streamlit: окружение готовит разработчик 1. Аналитика обязательно выполняется внутри pipeline-контейнера, а тесты — в сервисе tests. Не используй пути своего компьютера, зависимости вне образа и обязательную ручную подготовку на хосте.

## 1. Твой конечный результат

**Банковский акцент и задача для призового выступления:** подготовь проверяемые объяснения важного non-seed, узла с другим профилем и узла с неполной наблюдаемостью. В methodology.md добавь соответствие «наблюдение/ограничение → допустимый вывод → следующий шаг аналитика». Не зашивай демонстрационные gid в правила. После готовности MVP по возможности проверь чувствительность топа к одному ключевому порогу. Общая стратегия: [банковский сценарий и жюри](04-bank-and-jury.md).

`analyze(nodes, edges, transactions)` возвращает три DataFrame: `nodes_roles`, `clusters`, `top_nodes`. У всех исходных узлов есть объяснимая роль и кластер. Ранжирование воспроизводимо. При выборе произвольного gid ты можешь назвать реальные признаки, сработавшее правило, score и ограничения наблюдения.

Не требуется доказать преступность, обучить модель без разметки или угадать скрытую истинную классификацию. Качество оценивается по обоснованности критериев и полезности для проверки.

## 3. Шаг 1 — понять наблюдаемые данные

Получить от разработчика 1 профиль: типы, единицы, число узлов/рёбер/транзакций, self-loop, повторные пары, сверка сумм, seed и глубины. Если информации пока нет, изучать искусственные графы и строить код по объявленной схеме, а особенности реальных файлов согласовать после профиля.

Ключевые ограничения:

- Граф построен по исходящим переводам от seed до четырёх колен.
- У depth=4 отсутствие исходящих — обрыв наблюдения, а не доказанное оседание денег.
- У seed входящие неполные; у остальных тоже не видны все внешние потоки.
- По суммам внутри выборки нельзя восстановить полный банковский баланс.
- Малые переводы ниже порога и межбанковские операции не видны.
- Нет истинной разметки ролей; role_score не является статистически проверенной вероятностью.

В первую версию включить флаги ограничений. Даже если более сложная коррекция обрыва в ТЗ optional, делать категорический ошибочный вывод из него нельзя.

## 4. Шаг 2 — построить правильный граф

1. Отсортировать узлы по gid, рёбра по src/dst и создать направленный граф. Стабильный порядок входа нужен, чтобы перестановка строк не меняла результат алгоритмов со случайной выборкой.
2. **Сначала добавить все gid из nodes**, присоединив depth и is_seed.
3. Затем добавить рёбра src → dst с sum_kzt и n_tx. Это направление денег, не направление поиска «вышестоящего» узла.
4. Убедиться, что число вершин совпадает с nodes, а не только с объединением src/dst.
5. Сверить несколько пар и общую сумму рёбер с входными таблицами.
6. Посчитать слабосвязные компоненты, отдельно количество изолятов. Не смешивать компоненты сети с хотя бы одним ребром и полный граф со всеми изолятами.

При повторной паре DiGraph хранит одно ребро; поэтому разработчик 1 должен проверить агрегированность edges. Если нашли self-loop, согласовать и описать его обработку. Перевод самому себе не считать отдельным внешним плательщиком/получателем. Не удалять аномалии молча.

## 5. Шаг 3 — вычислить признаки каждого узла

Начни с таблицы, индексированной по полному nodes.gid. Присоединяй вычисленные метрики к ней через left join; отсутствующий поток заполняется нулём, неопределённое отношение остаётся отсутствующим.

| Признак | Как считать | Как использовать |
|---|---|---|
| in_degree | Число разных внешних плательщиков | Много источников — возможная консолидация |
| out_degree | Число разных внешних получателей | Много адресатов — возможное распределение |
| in_sum | Сумма наблюдаемых входящих рёбер | Масштаб полученного внутри выборки |
| out_sum | Сумма наблюдаемых исходящих рёбер | Масштаб отправленного внутри выборки |
| in_n_tx / out_n_tx | Суммы n_tx по направлению | Интенсивность операций |
| flow_ratio | out_sum / in_sum при in_sum > 0 | Только наблюдаемый коэффициент пропуска |
| observed_net | in_sum − out_sum | Наблюдаемая разница, не остаток счёта |
| is_boundary | depth == 4 | Неполная видимость исходящих |
| is_isolated | Нет входящих и исходящих рёбер | Недостаточно данных для структурной роли |
| n_seed_reachable | Число различных seed, от которых узел достижим по направленным путям; собственный gid не считать | Связь с несколькими исходными ветками |
| neighbor_clusters | Число других кластеров среди непосредственно связанных узлов | Межкластерная связность |
| betweenness | Посредническая центральность на направленном графе | Возможный структурный посредник, не доказанный организатор |

Для n_seed_reachable достаточно обхода достижимых вершин от каждого seed с учётом посещённых узлов; не перечислять все простые пути, их может быть слишком много. Повторная достижимость от одного seed увеличивает показатель только один раз. Циклы не должны вызывать бесконечный обход.

Для betweenness первая версия может использовать ограниченную выборку исходных вершин, например до 128, с фиксированным random seed. Сохрани режим и параметры в методологии. Если расчёт укладывается в общий лимит, точный вариант допустим. Не трактуй сумму перевода как длину пути: большие деньги не означают «более длинное расстояние». Для MVP центральность можно считать без денежных весов, а суммы использовать отдельным признаком.

Обязательно задать поведение для пустого графа, графа без рёбер, нулевой суммы входа и одинаковых значений признака. Нельзя оставлять inf/NaN в итоговых score.

## 6. Шаг 4 — кластеризация

Кластеры нужны до финальных ролей, если coordinator использует межкластерные признаки. Начальные признаки степени и суммы можно посчитать до них.

1. Сделать неориентированную проекцию для кластеризации. Между A и B вес = сумма A→B и B→A. В исходном направленном графе оба перевода сохранить отдельно.
2. Выбрать один базовый метод, например Louvain, с фиксированными параметрами и random seed.
3. Изолированные узлы назначить отдельным singleton-кластерам. Если граф целиком без рёбер, вернуть такие кластеры без вызова алгоритма, которому нужны положительные веса.
4. Проверить, что каждый gid получил ровно один cluster_id.
5. Сделать номера устойчивыми: отсортировать полученные множества по минимальному gid и присвоить последовательные целые номера.
6. Добавить в таблицу признаков число других кластеров среди соседей узла.

Нужно различать кластер и слабосвязную компоненту. В большой компоненте может быть несколько сообществ; номер кластера сам по себе не является оценкой опасности. Нельзя называть каждый кластер преступной группой.

## 7. Шаг 5 — выбрать объяснимые правила ролей

Следующие условия — **предложенная стартовая эвристика команды, а не требования организаторов и не проверенные выводы по данным**. Сначала посмотри распределения; затем зафиксируй конкретные пороги в коде и methodology.md. Менять пороги нужно по смыслу и устойчивости, а не по желанию получить определённые gid.

Предлагаемые начальные параметры:

- Много плательщиков: `in_degree >= max(3, Q75 положительных in_degree)`.
- Много получателей: `out_degree >= max(5, Q75 положительных out_degree)`.
- Существенный входящий поток: `in_sum >= Q75 положительных in_sum`.
- Кандидат транзита: наблюдаемый коэффициент 0.8–1.2.
- Малый наблюдаемый отток: коэффициент не больше 0.1.
- Высокая betweenness: не ниже Q90 положительных betweenness; если положительных значений нет, условие не выполнено.

Для пустого множества положительных значений соответствующее условие считать невыполненным. Для квантилей зафиксировать способ вычисления. В methodology.md сохранить фактические числовые пороги, получившиеся на выданном наборе, чтобы на защите не отвечать только «верхний квартиль».

| Роль | Начальное условие-кандидат | Что обязательно объяснить |
|---|---|---|
| consolidator | Много различных плательщиков и существенный входящий поток | Число источников, объём; наблюдаемый отток — дополнительная характеристика, не обязательное доказательство |
| distributor | Много различных получателей и положительный исходящий поток | Число получателей и отправленная сумма |
| transit | Есть входящие и исходящие, in_sum > 0, ratio в 0.8–1.2, узел не seed и не boundary | Соотношение наблюдаемых потоков; без временной проверки нельзя утверждать, что ушли именно те же деньги |
| terminal | Не seed, depth < 4, есть существенный входящий поток и ratio ≤ 0.1 | «Признаки конечного получателя в наблюдаемой выборке», а не доказанный остаток |
| coordinator | Высокая betweenness, достижимость минимум от 2 различных seed и связи минимум с 2 другими кластерами | Структурный кандидат на координацию; объяснить все три наблюдения |
| peripheral | Нет достаточной поддержки других правил, либо изолят | Почему данных/структурных признаков недостаточно; «периферия» не означает доказанную безопасность |

Условия могут пересекаться. Для первой версии зафиксировать понятный порядок выбора одной основной роли: изолят → peripheral; затем coordinator → distributor → consolidator → terminal → transit → peripheral. Это проектное соглашение, его нужно проверить на синтетических примерах и описать. Если порядок меняется, обновить тесты и методологию вместе.

Не добиваться присутствия всех шести названий искусственно. Все правила должны быть реализованы, но если роль не получила ни одного обоснованного кандидата, исследовать причину и объяснить результат. Правила должны классифицировать фактические признаки, а не выполнить квоту.

Граница depth=4 запрещает вывод terminal/transit только по отсутствующим исходящим. При этом входящие реально наблюдаются, поэтому пограничный узел может иметь признаки консолидации с явной оговоркой о неполной картине. Seed может иметь структурные роли distributor/coordinator/consolidator; запрет относится к ненадёжной интерпретации баланса.

## 8. Шаг 6 — role_score

role_score оценивает поддержку выбранной гипотезы наблюдаемыми признаками. Его нельзя выдавать за вероятность преступности, качество модели или accuracy.

Практический вариант: определить `S(x, t) = min(1, max(0, x / t))` при t > 0; при недоступном пороге S = 0. Для каждого правила определить 2–3 составляющие и взвешенное среднее. Например, для consolidator — сила числа источников и входящего объёма; для distributor — числа адресатов и исходящего объёма; для coordinator — центральности, seed-достижимости и межкластерных связей.

Насыщение признаков можно считать относительно более сильного порога, например Q95, чем порог допуска Q75. Иначе каждый прошедший правило получит одинаковую единицу. Для ratio в transit использовать близость к 1, например `max(0, 1 - abs(ratio - 1) / 0.2)`, совместно с силой реальных входящих/исходящих связей, не как единственный score.

Для terminal высокую поддержку даёт малый наблюдаемый отток и выраженный вход; для peripheral разумно явно зафиксировать 0 как отсутствие поддержки содержательной роли, особенно у изолятов. Не показывать изоляту «100% уверенности», которую пользователь может принять за уверенность в безопасности.

Первоначальные ограничения уверенности допустимо реализовать как документированные верхние границы: например не выше 0.5 для гипотез на depth=4; не выше 0.7 для transit/terminal без временной проверки. Это **не калиброванные значения**, а предложенная консервативная политика отображения. Выбрать и проверить их явно, не менять скрыто.

Достаточно одного прозрачного способа; не строить отдельную ML-модель score в пятичасовом MVP. В итоговых CSV запрещены NaN/inf и значения вне [0,1].

## 9. Шаг 7 — priority_score и топ

Приоритет проверки отличается от поддержки роли: крупный неоднозначный узел может заслуживать проверки раньше небольшого хорошо объяснённого. Не присваивать одинаковые priority_score всем consolidator.

Предлагаемая первоначальная формула:

```text
priority = 0.35 * V + 0.25 * D + 0.25 * C + 0.15 * R
```

- V — нормированный `log1p(in_sum + out_sum)`, масштаб наблюдаемой активности.
- D — нормированное число уникальных внешних соседей, объединение плательщиков и получателей без двойного счёта одного контрагента.
- C — нормированная betweenness, структурная посредническая значимость.
- R — нормированное n_seed_reachable, связь с исходными направлениями расследования.

Это пример эвристики; веса не подтверждены разметкой. Зафиксировать их, проверить чувствительность и объяснить смысл. Для простого нормирования использовать `(x - min) / (max - min)` по всем узлам; при max == min результат признака = 0. Если измените нормировку, документировать новую. Понижать приоритет seed только потому, что он seed, не обязательно: это отдельное предметное решение.

1. Посчитать score для всех узлов.
2. Отсортировать по score по убыванию, затем gid по возрастанию.
3. Взять первые 20 на полном наборе; rank от 1.
4. Сформировать why из 2–3 значимых вкладов: масштаба, числа контрагентов, центральности, достижимых seed.
5. Сверить роли и score между топом и полной таблицей.

В топе могут быть и seed, и non-seed. На демо отдельно показать, какую дополнительную ценность даёт нахождение важных non-seed; не исключать seed из общего ранжирования тайно.

## 10. Шаг 8 — объяснения и кластеры

Для evidence использовать шаблоны с фактическими значениями. Например: «12 плательщиков, вход 8.4 млн KZT; наблюдаемый отток 6%. Признаки консолидации». Это **пример формулировки на вымышленных числах**, а не результат по реальному gid.

Для boundary: «9 плательщиков, вход 3.1 млн KZT. Признаки консолидации; depth=4, исходящие наблюдаются неполно». Для изолята: «В выгрузке нет наблюдаемых переводов; данных для структурной роли недостаточно». Для coordinator избегать «организатор преступной группы»: писать «структурный кандидат для проверки».

Сначала резервировать место под критичное ограничение, потом собирать текст в пределах 200 символов. Не обрезать строку вслепую так, что исчезает «исходящие неизвестны». Значения округлять только для человекочитаемого текста.

По каждому кластеру посчитать n_nodes, n_seed, sum_kzt_internal; выбрать до пяти gid с максимальным priority_score. hypothesis — короткое описание наблюдаемой структуры: например несколько источников и одна выраженная точка сбора. Если структура не выражена, так и написать; не придумывать назначение фирмы или тип преступления.

## 11. Шаг 9 — meaningful-проверки

| Искусственный случай | Что проверяет |
|---|---|
| Изолированный seed | Не пропадает; есть peripheral, cluster_id и объяснение |
| Несколько источников → один центр | Правило консолидации и число уникальных плательщиков |
| Один отправитель → много адресатов | Распределение и направление связей |
| A → B → C с близкими суммами | Кандидат транзита при выполненных ограничениях |
| Получатель depth=3 с малым наблюдаемым оттоком | Кандидат terminal с осторожным текстом |
| Тот же профиль на depth=4 | Не становится terminal только из-за обрыва |
| Seed с out_sum > in_sum | Не трактуется как доказанный отрицательный баланс |
| Цикл A → B → C → A | Обход завершается, seed не считается многократно |
| Встречные A↔B | Проекция суммирует веса; исходные направления сохранены |
| Две компоненты и изолят | Все вершины получают кластер |
| Несколько одновременно подходящих правил | Соблюдается описанный порядок выбора роли |
| Одинаковый вход дважды | Совпадают роли, нумерация кластеров, порядок топа |
| Перестановка строк входа | Результаты остаются теми же после принятой сортировки входов |
| Все значения метрики равны нулю | Нормировка не даёт деление на ноль |

Ожидаемые результаты тестов выводить из описанных правил, не из первого случайного запуска. Маленький граф может требовать явных тестовых порогов или достаточно большого веера; это не разрешение хардкодить production-gid.

На реальных данных посмотреть распределение ролей/score, долю depth=4 в terminal, наличие всех изолятов, пять верхних узлов и несколько случайных. «Топ выглядит правдоподобно» не заменяет инварианты, но помогает обнаружить слабую эвристику.

## 12. Шаг 10 — методология и подготовка к жюри

В docs/methodology.md должны быть:

1. Как построен направленный граф и что означают веса.
2. Формулы каждого используемого признака, обработка нулей/неполноты.
3. Метод кластеризации, random seed, способ нумерации, работа с изолятами.
4. Все шесть правил и их порядок; реальные числовые пороги.
5. Формулы role_score и priority_score; зачем нужны оба.
6. Ограничения depth=4, seed, периода и порога транзакций.
7. Примеры реально рассчитанных узлов и объяснения без выдуманных полей.
8. Что изменится на графе около миллиона узлов: стоимость центральностей, более экономное хранение, ограничение отображаемых подграфов. Реализация масштаба не нужна.

Для демо выбрать после расчёта: выраженный важный non-seed; узел с другой ролью; boundary/изолят, на котором видно честную обработку ограничений. Заучивать только эти gid нельзя — нужен поиск и объяснение любого узла.

## 14. Если останется время

Первое разумное улучшение — временная поддержка transit. На дневных данных можно показывать, какая доля исходящей активности приходится на день входящей или следующие 1–2 дня. Это признак совпадения по времени, не доказанное сопоставление конкретных денежных средств. Не описывать простое совпадение дат как точную трассировку одной суммы.

Второе — повторяющиеся связи/циклы как дополнительные наблюдения. Ни одно улучшение не должно ломать обязательные схемы или выводить расчёт за пять минут. LLM-пояснение не должно подменять рассчитанные факты.
