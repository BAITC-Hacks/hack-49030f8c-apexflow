# Общий договор команды: входы, выходы, интеграция

Этот документ задаёт договор модулей. Реализация пайплайна, аналитики и UI есть
в интегрированных ветках; фактические проверки и ограничения перечислены в
[протоколе приёмки](../acceptance.md). Числа из ТЗ не заменяют проверку файлов.
Главный план — `TEAM_PLAN.md` в корне.

## 1. Кто за что отвечает

| Кто | Зона ответственности | Ветка | PR |
|---|---|---|---|
| Разработчик 1, другой участник | Входные данные, CLI, запись CSV, Docker/Compose, зависимости, контейнерный CI, интеграция | Собственная от staging, пример `dev/pipeline` | В staging |
| Разработчик 2, Максим | Граф, признаки, роли, score, кластеры, топ, методология | `codex/dev-maxim` | В staging |
| Разработчик 3 | Экран, поиск, карточки, документация для жюри, демо | Собственная от staging, пример `dev/ui` | В staging |

Имена веток участников 1 и 3 — примеры, они выбирают свои. `main` означает production; отдельной `prod` нет. Новая функция проходит путь личная ветка → PR в staging → проверки интеграции → release PR staging → main.

## 2. Что договориться сделать в первые 20 минут

1. Разработчик 1 публикует первоначальную staging, если её ещё нет на GitHub. Существующие файлы планирования сначала коммитятся в личной ветке и передаются в staging через PR; `git add .` для этого не использовать: рядом лежат данные, PDF и системный `.DS_Store`.
2. Все получают одинаковые три Parquet. Способ хранения согласовать с организаторами; ключи, виртуальные окружения и локальные служебные файлы в Git не попадут.
3. Сравнить SHA-256 каждого входного файла между компьютерами. В Git передавать хэши и агрегированный профиль, если публикация самих данных не согласована.
4. Разработчик 1 проверяет существование колонок, назначает версию Python внутри Docker-образа, фиксирует первоначальные зависимости и создаёт минимальный Compose. Версии сохраняются после проверки установки, а не выбираются по памяти.
5. Все принимают сигнатуру `analyze` и три схемы CSV ниже. Изменение этого договора сообщается двум другим участникам до реализации.
6. Разработчик 3 начинает UI на явно отмеченном синтетическом примере; Максим начинает алгоритмы на маленьких искусственных графах; разработчик 1 проверяет I/O и CLI. Никто не должен ждать полностью готовую соседнюю часть.

## 4. Входные DataFrame

Названия взяты из ТЗ. Разработчик 1 сверяет их с реальными Parquet до написания загрузчика.

| Таблица | Обязательные поля | Назначение |
|---|---|---|
| nodes | `gid`, `depth`, `is_seed` | Полный список клиентов, включая изоляты |
| edges | `src`, `dst`, `sum_kzt`, `n_tx`, `depth` | Агрегированное направленное ребро плательщик → получатель |
| transactions | `src`, `dst`, `date`, `sum_kzt` | Отдельные операции для проверки агрегатов и временных признаков |

Правила передачи между участниками:

- gid/src/dst — целые int64 без пропусков; идентификаторы не преобразуются через float.
- depth — целое; ожидаемый диапазон по ТЗ 0–4. Значение за пределами диапазона — ошибка/расхождение профиля, которое нужно выяснить.
- is_seed — настоящий bool. Строку `"False"` нельзя превращать в bool обычным `bool(...)`.
- Денежные значения должны быть конечными. По данным определить единицы и точность; не отбрасывать дробную часть произвольным `astype(int)`.
- n_tx — положительное целое. Все src/dst должны присутствовать в nodes.
- date — разобранная календарная дата/временная метка. Если источник даёт только день, не придумывать время и точность до часов.
- В исходном nodes gid уникален. В edges ожидается одна строка на направленную пару; дубликаты выяснить, а не терять при добавлении в DiGraph.
- Совпадающие строки transactions могут обозначать разные реальные переводы: без transaction_id автоматически удалять их как дубликаты нельзя.
- Отсутствие столбца, неразбираемый тип и ссылка на неизвестный gid — явная ошибка входа; не скрывать их заполнением нулями.

## 5. Python-интерфейс между разработчиками 1 и 2

```python
# src/apexflow/analytics.py — реализует Максим
def analyze(nodes, edges, transactions):
    """Возвращает три таблицы, не пишет файлы и не меняет входные DataFrame."""
    return {
        "nodes_roles": nodes_roles,
        "clusters": clusters,
        "top_nodes": top_nodes,
    }
```

Ожидания: все входы уже провалидированы; результат детерминирован при одинаковых данных/версиях/настройках; функция не делает сетевых запросов; не читает скрытые глобальные пути; все обязательные расчёты доступны без ключей API. Аналитические ошибки не заменяются пустыми таблицами.

Разработчик 1 импортирует ровно эту точку входа. UI не импортирует `rules.py` и не присваивает роли заново. После готовности общей аналитики нельзя оставить в production заглушку, которая назначает всем peripheral только ради прохождения проверки числа строк.

## 6. Схемы CSV

### nodes_roles.csv

| Поле | Тип/условие |
|---|---|
| gid | int64; ровно один раз каждый gid из nodes |
| role | consolidator / transit / distributor / terminal / coordinator / peripheral |
| role_score | Конечный float от 0 до 1; эвристическая поддержка роли, не вероятность преступления |
| cluster_id | Целое; существует в clusters |
| priority_score | Конечный float от 0 до 1; приоритет аналитической проверки |
| evidence | Непустой понятный текст до 200 Unicode-символов, с числовыми наблюдениями |

### clusters.csv

| Поле | Тип/условие |
|---|---|
| cluster_id | Уникальное целое |
| n_nodes | Число узлов с этим cluster_id |
| n_seed | Число seed в кластере по nodes, включая изоляты |
| sum_kzt_internal | Сумма рёбер, у которых оба конца внутри кластера, каждое исходное ребро учитывается один раз |
| top_gids | JSON-массив целых в CSV-ячейке; предлагаем не более 5 узлов, по убыванию priority_score |
| hypothesis | Непустая гипотеза, основанная на фактах; для изолята — отсутствие наблюдаемых связей |

### top_nodes.csv

| Поле | Тип/условие |
|---|---|
| rank | Последовательные целые от 1 |
| gid | Уникальный существующий gid |
| role | Совпадает с nodes_roles |
| priority_score | Совпадает с nodes_roles |
| why | Числовое объяснение приоритета, не просто повтор названия роли |

Базовый объём топа — 20. На полном наборе обязателен топ не менее 20; на искусственном тестовом графе из N < 20 узлов допускается min(20, N). Это исключение тестового режима не ослабляет приёмку хакатонного набора.

Общие настройки: UTF-8, запятая, заголовки строго по указанному порядку, `index=False`, корректное CSV-экранирование. nodes_roles сортировать по gid; clusters по cluster_id; top_nodes по priority_score по убыванию, затем gid по возрастанию. Перед сохранением не округлять score настолько, что меняется порядок равных отображаемых значений; в UI округлять только показ.

## 7. Договор с интерфейсом

UI получает три CSV из output и исходные nodes/edges для атрибутов и связей. Свойства окна: поиск, выбранная роль, кластер и размер окружения не меняют сохранённые аналитические результаты.

Карточка показывает role, evidence, role_score, priority_score, cluster_id, depth, is_seed и наблюдаемые связи. Число контрагентов и суммы UI может вычислить из edges для показа. Формулы этих простых наблюдаемых величин должны совпадать с методологией Максима. Решения о роли и приоритете всегда берутся из CSV.

Свежесть набора подтверждает `output/run_manifest.json`: версия схемы, состояние
running/failed/complete, SHA-256 всех трёх входных Parquet и трёх CSV, версия кода,
зависимости, время и размеры результата. Это служебный файл рядом с тремя
обязательными CSV; схемы выгрузок и API analyze сохранены.
Пайплайн сначала инвалидирует предыдущий успешный запуск, а complete публикует
только после проверки и записи всех файлов. UI допускает только complete и
совпадающие хэши. При отсутствии manifest, ошибке или изменении исходников
нужен новый расчёт. Явный синтетический режим работает отдельно от файлов.

## 8. Целевые команды и ошибки

**Docker — обязательный основной способ запуска.** Пайплайн, вся аналитика, UI и тесты работают в контейнерах. Разработчик 1 владеет Dockerfile/Compose и контейнерным CI. На хосте остаются Docker с Compose, Git/редактор, браузер, исходные файлы и сохранённые результаты; локальный Codex/SkillSpector тоже не требуется переносить в приложение.

Одна runtime-база используется сервисами pipeline и ui с разными командами; tests использует ту же базу с добавленными тестовыми зависимостями и включается отдельно. Не создавать отдельный сервис для каждого аналитического модуля. UI зависит от **успешного завершения** pipeline, а не только от факта запуска его контейнера.

Монтирование: `./data` → `/app/data` только для чтения у pipeline и ui; `./output` → `/app/output` с записью у pipeline и только чтением у ui. Результаты сохраняются на хосте после удаления контейнеров. Реальные данные и output не включаются в образ. Тесты используют временную папку результатов вместо перезаписи output для демо.

Команды основного сценария; результаты их проверки записаны в протоколе приёмки.

```bash
# Полный сценарий: пересчёт, затем интерфейс
docker compose up --build --force-recreate
# Тесты в отдельном контейнере
docker compose --profile test run --rm --build tests
# Остановка без удаления входных файлов и результатов
docker compose down
```

Целевой адрес UI — http://localhost:8501. Внутри контейнера сервер слушает 0.0.0.0, а локальный порт хоста публикуется на 127.0.0.1. Разработчик 1 проверяет основной сценарий на своей системе и вместе с коллегами — на используемых в команде платформах/архитектурах. Не заявлять переносимость без проверки. Локальный Python-запуск допустим как дополнительный режим отладки, но не заменяет контейнерную приёмку.

При повторном расчёте сначала остановить работающий UI (`docker compose down`), затем выполнить основной запуск; не читать CSV в момент их перезаписи. `--force-recreate` гарантирует новое выполнение pipeline вместо опоры на контейнер предыдущего успешного расчёта. Время скачивания/сборки образа измерять отдельно от пересчёта данных, который внутри контейнера должен укладываться в 5 минут.

CLI возвращает код 0 только после проверки и успешной записи трёх результатов; при ошибке — ненулевой код с понятной причиной. При неудачном пересчёте старые CSV не объявляются свежими. UI сообщает об отсутствующих/повреждённых файлах и показывает команду пересчёта.

## 9. Проверки на границах модулей

| Что проверяем | Кто отвечает | Что считается ошибкой |
|---|---|---|
| Входная схема и профиль | Разработчик 1 | Неизвестные gid, пропуски, сломанные типы |
| Смысл и ограничения признаков | Максим | Полный баланс выводится из неполной выборки; изолят исчезает |
| Роли и объяснения | Максим | Необъяснимая роль, выдуманные факты, неверный terminal для границы |
| Согласованность трёх CSV | Разработчик 1 | Потеря узлов, NaN, несовпадение score, неверные n_nodes/n_seed |
| Граф и поиск | Разработчик 3 | Стрелки перевёрнуты, часть gid не находится, несвязанный узел скрыт |
| Полный сценарий | Все; запускает разработчик 1 | Зависимость от ручного шага, ошибка UI, >5 минут |

## 10. Как согласовывать изменения

Конкретные задачи и контрольные точки перечислены в [рабочей карте](05-execution-and-acceptance.md). У каждого этапа есть владелец, входные зависимости и способ приёмки; до проверки его статус не считается успешным.

Сообщение о готовности модуля содержит: название ветки/PR; что уже работает; точную команду проверки; какие файлы/интерфейсы изменены; что ещё не готово. Сообщение «всё сделал» без команды и результата недостаточно.

Если нужен новый столбец, функция или зависимость: сначала описать потребителя и причину, затем согласовать с владельцем. Не добавлять обязательные поля в CSV из ТЗ по собственной инициативе. Расширения после MVP оформляются отдельно.

Пары для ревью: работу разработчика 1 смотрит Максим; аналитику Максима смотрит разработчик 1, понятность объяснений — разработчик 3; UI и инструкцию запуска смотрит разработчик 1, корректность фактов в карточке — Максим.

## 11. Приоритет и граница объёма

Проект создаётся для банка с целью занять призовое место. Общая [стратегия для банковского сценария и жюри](04-bank-and-jury.md) уточняет приоритеты: проверяемая карточка расследования, воспроизводимость, честная обработка ограничений и измеренные результаты. Она не добавляет обязательные поля в три CSV и не требует внешних данных/LLM. Рекомендации следующих действий определяются Максимом по наблюдениям и ограничениям, отображаются разработчиком 3 и не выполняют действия во внешних банковских системах.

Сначала весь обязательный сценарий, затем качество объяснений и демо. После этого возможны временные признаки и карточка с дополнительными наблюдениями. Чат-бот, GPU, внешний enrichment, база данных, микросервисы и обучение без размеченных ролей не входят в обязательный план.

Примерно к 02:30 нужен первый сквозной запуск; к 03:30 — все must-have; с 04:15 — только исправления, проверка воспроизводимости и сдача. Новая фича не должна сорвать работающий результат.
